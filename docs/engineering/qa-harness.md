# QA harness

Run from the repository root with installed dependencies and system Google Chrome:

```sh
pnpm qa
# Use the run ID printed with the report:
pnpm qa:perceive <run-id>
# During a fix, inspect one registered screen:
pnpm qa:perceive <run-id> inbox
```

`pnpm qa` builds the workspace, starts its own loopback Vite preview, captures and checks every registered state, measures performance, and closes Chrome and the server. An optional positional run ID (`pnpm qa my-run`) must be new. `XP_BASE_URL` selects an already running app instead; that server remains the caller's responsibility. Direct `node scripts/qa/capture.mjs` requires a current build. The harness uses `channel: "chrome"`, with no browser download, and takes its browser driver from `@playwright/test` in `apps/web`; the repository has no dependency on the separate `playwright` package.

Route probes use visible module links. When M or TP places a destination in its module sheet, the
probe opens and settles that chooser before the measured destination click. The measured route window
includes chooser dismissal; the six warmed transitions, cold/warm-up diagnostics and timing thresholds
are unchanged. Overflow checks permit a semantic `nav` with explicit horizontal scrolling, as required
for the vision's compact section strip; hidden clipping, ordinary content overflow and document overflow
still fail and have separate regression fixtures.

## Coverage and artifacts

`apps/web/src/qa/screens.ts` is the screen registry: route path, module, display name, route file, and states. Add every JSX/TSX route component, including nested routes; keep route helpers in `.ts` files or outside `src/routes`. The web unit suite recursively compares route files with registry entries and fails for missing, stale or duplicate entries. Add module state setup and a readiness assertion in the producer named by `qa.states` in `apps/web/src/app-modules.ts`; generic states stay in `scripts/qa/common.mjs`, and an unsupported state fails capture.

Current states: dashboard default/navigation open/panel open; inbox default/navigation open/empty search/selected conversation/panel open; settings default/navigation open/saved/panel open; kit sixteen gallery/record states plus its two inspector-pane states; configure default/panel open. `sheet-open` names the shared navigation-open intent: compact classes render a sheet and larger classes use their native overlay form. `panel-open` names a route's inspector pane, and every route that has one registers it: all five do. `apps/web/tests/qa-registry.test.mjs` fails a route that hands `RoutePanes` an inspector and registers no pane state, because that is how four of the kit's five per-class forms went uncaptured through a 540-case run. The kit registers two, its gallery pane and its record pane (`record-panel-open`). One `openRoutePane` helper opens all of them in the class's own form, so a new module registers the state without teaching the harness a new selector. DS and DW dock the pane; TL, TP and M open it from the labelled trigger. A docked pane enters from opacity 0 at scale 0.96, and Playwright counts an element as visible on a non-empty box alone, so the helper waits for the pane's resting geometry as well; without that wait a `panel-open` case measures and photographs a pane that is not on screen yet. The configurator's five-frame preview strip is deliberately not a registered state: the founding-failure detector is right to refuse a phone page that scrolls five device frames, so on M and TP the strip is opt-in and `apps/web/tests/configurator.browser.mjs` verifies it in all five classes instead. Each state runs at M 390x844, TP 768x1024, TL 1024x768, DS 1366x768 and DW 1920x1080, in light and dark, with normal and reduced motion. Fresh contexts isolate each case. The inner simulator parameters `?xp=<class>&xp-frame=1` preserve the actual canonical viewport without the outer preview toolbar.

Thirty-two states produce 640 cases and 1,280 PNGs. Each case gets full-page and first-viewport images. Full-page refers to the browser document; nested scroll panes remain at their initial position. Geometry checks also inspect those panes. Progress prints as `[n/640]`, and five consecutive setup failures abort the run with the last error, so a broken selector surfaces in seconds instead of after the whole matrix. Outputs are gitignored under `apps/web/evidence/<run-id>/`:

- `<screen>-<class>-<mode>-<state>-<motion>-<crop>.png` and matching `.json`: dimensions, gate verdicts, measured sample counts, geometry and capture identity per shot.
- `manifest.json`: every case, including capture failures, browser version and performance measurements.
- `qa-report.md`: per screen/class verdict counts, a gate-activity table, the performance table with one row per measured window, individual failures, and the list of gates that observed nothing.
- `perf.json`: every repetition's per-window timestamps, measured/expected intervals, dropped frames, active elapsed time, verdict and host snapshots, plus the selected median run for each interaction.
- `perceiver-prompt.md`, `perceiver.md`, `perceiver-process.log`: exact visual-review input, final answer and process diagnostics.

`XP_QA_MODULES=auth,settings pnpm qa <id>` restricts a run to the listed registry modules (the `module` field of `apps/web/src/qa/screens.ts`); an unknown name, or a set but empty list, fails the run and prints the known modules. The manifest records `partial: true` with the module list and the report opens with a PARTIAL RUN line, so a filtered run can never be mistaken for the registry run. Builders iterate on a filter to keep fix rounds short on the shared host; the run that qualifies a PR and the reviewer's run are unfiltered, because a module change can regress a shared kit or shell surface that only the full matrix photographs.

The original `pnpm --filter web evidence` remains available for the #36 behavioral and contrast regression checks. This harness supersedes its screenshot matrix for module QA; it does not remove that separate regression coverage.

Capture omits Chrome's default `--hide-scrollbars` argument. Native scroll affordances are part of the
rendered UI evidence: suppressing them makes a correctly bounded form or article look permanently
clipped. The inbox browser suite uses the same launch setting. This changes screenshot presentation,
not scroll bounds, accessibility requirements or performance thresholds.

## Setup contract

Each case navigates to the simulator URL, waits for `html[data-xp-class]`, then asserts that the route's own `H1` matches the registry `name` for that screen. A route that renders blank therefore fails at setup instead of letting every DOM gate pass over an empty document.

Offers also waits for its collection records to reach full opacity and zero translation. Their first-paint fade runs independently of button feedback; waiting for unscaled controls alone can capture an empty record deck under host contention. A collection that never appears fails setup.

Colour mode comes from emulated media, never from clicking the theme control: the app's preference is `system`, so `page.emulateMedia({ colorScheme })` drives `data-theme` through the shared theme runtime. Setup then asserts that `data-theme` actually followed the emulated scheme, so a broken theme runtime fails loudly rather than capturing 180 light screenshots labelled dark. A capture that needs an explicit preference instead of the OS query sets the `xp-theme-mode` storage key or calls `setThemePreference` from `@xp/theme`; the three segmented-control radios measure 0x0 inside the header popover and cannot be clicked.

## Machine gates

Every gate reports how many elements or samples it inspected, and a gate is one of four statuses. `FAIL` has findings. `PASS` means the gate inspected at least one sample and found nothing. `NA` means the gate does not apply to this case (reduced motion outside reduce runs, the founding-failure detector outside M, focus trap with no overlay). `INACTIVE` means the gate applies but observed nothing at all, and it is never counted as a pass. A case is PASS or FAIL on its gates alone; its inactive gates are listed in their own report column, in the gate-activity table and in a closing section, so a clean case never implies that every check ran.

| Gate | Failure condition | Inactive when |
|---|---|---|
| Overflow | Document scrollWidth exceeds clientWidth, or a visible element overflows horizontally by more than 1px (rounding allowance). Two designed patterns are excluded: native input/textarea/select value scrolling, and a declared truncation (`text-overflow: ellipsis` with a clipping `overflow-x`, or a `-webkit-line-clamp`). Clipping without either still fails, because that hides content silently. Overflowing parent containers still fail, and other intentional horizontal scrollers are reported for review. | No visible element measured. |
| Tap targets | Enabled visible interactive hit area is below 44px on either axis on M/TP or below 24px on TL/DS/DW (vision §6.3). Native associated labels count as hit areas; negative margins preserve the measured button box while allowing it to overhang compact visuals. | No enabled visible interactive element measured. Applies to all five classes, never desktop NA. |
| Text | Visible text or a form value has a computed font size below 12px. | No visible text or form value measured. |
| Console | Any browser console error or uncaught page error from navigation through capture. | Never: the listeners are attached for the whole case. |
| Alt | A visible image lacks an alt attribute; explicit empty alt for decoration is valid. | No visible `img` element measured. Inline SVG icons are not images. |
| Focus trap | An overlay does not receive focus, or Tab/Shift+Tab escapes over more than one complete traversal. Whether an overlay is expected is read from the rendered document (an open shell sheet, or a centred kit dialog) rather than from a list of state names, so a newly registered state whose form is a modal is armed without editing the harness. | The open dialog has no focusable element, so traversal proves nothing. NA with no modal overlay; native non-modal popovers deliberately do not trap Tab. |
| Founding failure | The matching DW document fits its own viewport (within the same 1px allowance the overflow gate uses) and M's effective page height exceeds 1.25 times its viewport. M's effective height includes the largest nested content scroll excess, so a fixed-height shell cannot hide stacked content. | The DW baseline does not fit its viewport, so a stacked M form cannot be judged. Nested DW pane scrolling does not disarm it; only a DW document that scrolls does. NA outside M. |
| Animation budget | Computed visible transition/animation duration plus delay exceeds 300ms, or an active animation exceeds the budget. Rare launch surfaces must opt in with `data-qa-motion="launch"` and a `--xp-dur-launch` duration. | No declared non-zero duration and no active animation. These checks are evidence, not a claim that every accessibility or design defect is machine-detectable. CSS checks cover the captured state; image review cannot prove behavior. Browser fixtures verify that intentionally defective DOM fails, corrected DOM passes, and an empty document reports zero measured samples instead of a clean sweep.

## Performance

Capture calls `scripts/qa/perf.mjs`. To repeat only performance against a current build: `node scripts/qa/perf.mjs <existing-run-id> --repeat 3` (updates `perf.json`; preserve an earlier file before rerunning, and re-run full QA for a synchronized report). Three repetitions are the default in both capture and the standalone probe. `--repeat` accepts a positive odd integer, including 1 for diagnostics (FAIL if that repetition conclusively fails; otherwise INCONCLUSIVE because PASS certification requires at least two conclusive repetitions).

Capture closes the screenshot browser and launches a fresh one before the performance gate, so the benchmark runs in a process that has not just held hundreds of contexts. That matches the standalone probe's browser lifetime, and it is also a deliberate change to the numbers: cadence figures from a run before this change are not directly comparable with figures after it.

### Host eligibility (#78, round 3)

Before and after every repetition, record `os.loadavg()` (1/5/15 minutes), `os.cpus().length`, `os.freemem()` in bytes, and `ps` counts of other Chrome/Chromium processes and browser processes. The browser PID comes from CDP; exclude that browser and its descendant processes. Helpers count in the total process count, but only browser roots count against the browser threshold. Snapshots appear in JSON, standalone console output and the capture report.

If the **before** snapshot has a 1-minute load average **greater than cores * 0.6** (6 on this 10-core M4), **or more than one other Chrome/Chromium browser process**, a measured cadence repetition and its cadence windows are **INCONCLUSIVE**, never PASS or FAIL. This classification applies only to measured cadence: functional failures and unmeasured results retain their verdict on every host. Record the reason and retain all raw measurements, including cold/warm-up windows. Equality at either threshold is eligible. The after snapshot is retained for inspection; it does not change this explicitly before-based classification. Free memory is evidence, not an additional eligibility threshold.

Why: the Operator reports that round-2 failing probes overlapped four other agents running Chrome QA, with 1-minute load 24-30 on a 10-core M4. Cadence verdicts under contention are not evidence either way. Builders and reviewers must report cadence honestly under load; the Operator certifies cadence on a quiet host **before every merge**. A FAIL measured on a quiet host is a real defect. Do not retry until PASS or treat INCONCLUSIVE as acceptance.

With DOM gates passing, `pnpm qa` exits **0** only when every perf interaction is PASS, and **2** when perf is INCONCLUSIVE without a real failure. It prints: `cadence not certified on this host: rerun perf on a quiet host before merge`. DOM failures or conclusive perf failures (including INACTIVE) take precedence and exit **1**. Standalone perf uses the same perf exit policy.

The probe uses Chrome CDP at 4x CPU throttle and samples requestAnimationFrame strictly inside active interaction windows, mirroring `apps/web/scripts/motion-fps.mjs`. It measures M 390x844, TP 768x1024, TL 1024x768 and DS 1366x768 in light mode with normal motion and touch capability. DW remains covered by the capture matrix and shell browser suite, not this cadence probe. There is no fixed settle padding; bounded two-frame quiet tail after route mutations.

- Four route probes: `route-transition` (M bottom tabs), `route-transition-TP` (top navigation), `route-transition-TL` (icon rail), and `route-transition-DS` (sidebar). Each measures the three destinations in `qa.perfRoutes` from `apps/web/src/app-modules.ts` twice, six real client-side navigations, each its own window. A window opens on the click and closes when the new route's own `H1` is in the document, the route lifecycle has removed the outgoing pane, and a MutationObserver has seen no change for two frames. The landing pathname is verified for every navigation. The wired shell animates route panes; the window includes their style mutations and descendant mutations until the route is quiet. Requiring one remaining pane prevents an early quiet gap during a busy mount from truncating the measurement before GSAP finishes; a browser fixture reproduces that premature 33ms window and verifies the completion boundary.
- `sheet-drag` is the fifth interaction, on M only: one continuous window that opens on pointer down and closes on pointer up, with no release settle. After opening More and waiting for its surface to rest, 45 pointer steps drag down and reverse. The sheet's own position is sampled every frame in the page, so no per-step round trip inflates the window, and a drag that displaces the sheet less than 5px fails instead of reporting an idle 60 fps.

Before the six measured repeat navigations, the probe measures the first Inbox visit as `cold first transition`, then measures a warm-up return to Overview. Both windows have their own dropped-frame verdict (INCONCLUSIVE on a loaded host) and remain in `perf.json` (`coldWindow`, `warmupWindow`) and `qa-report.md` for every repetition, including failures. They are excluded from the warmed aggregate and median selection: a warmed PASS does not certify cold cadence. The first Settings visit is still inside the six gated windows. Cold means first navigation in a fresh context after normal setup (`networkidle`, route heading, fonts ready), not a click racing the initial page load.

This warm-up policy is conditional on the product's post-paint idle work: GSAP timeline initialization and prefetch/evaluation of the sole lazy route, the motion lab. Inbox, Settings and Overview already ship eagerly in the entry module and need no route fetch. Client-side arrivals use the pane entrance without a nested row stagger; direct Inbox loads retain first-paint stagger. The extra navigation separates repeat cadence from the residual first-mount layout cost; it is not evidence that cold cost disappeared. Missing/failed navigation still fails probe setup.

FPS is measured intervals divided by active time. Each window counts `expectedIntervals = round(elapsedMs / 16.667)`, `measuredIntervals = samples - 1`, and `dropped = expectedIntervals - measuredIntervals`. It passes with `dropped <= 1` and fails with `dropped >= 2`; there is no per-window FPS floor. Why: the previous 50 fps floor accepted two dropped frames in a 233.33 ms window, contradicting the intended rule that the second dropped frame fails. Regression fixtures cover 13 samples over 233.33 ms (two drops, FAIL), 14 samples (one drop, PASS), 12 samples (three drops, FAIL), and 21 samples over 383 ms containing a 49.9 ms gap (three total drops, FAIL). A gap alone does not establish the total drops; the whole window does.

Each interaction runs three times, in fresh browser contexts per class (M route and drag share their context), without early exit or replacement retries. The repetition order is M route/drag, TP route, TL route, DS route. Exclude INCONCLUSIVE repetitions from selection only, retaining them in the report. **Any conclusive FAIL makes the interaction FAIL and exits 1**, regardless of other repetitions: one quiet FAIL plus two loaded INCONCLUSIVE repetitions is FAIL. `failedRun` identifies the decisive failure; `medianRun` is null because failure precedence bypasses median selection. Only when there is no conclusive FAIL do fewer than two conclusive repetitions make the interaction INCONCLUSIVE. The minimum-two rule is a certification requirement, never a reason to hide a failure. Otherwise sort conclusive runs by unrounded aggregate FPS and select the middle run independently for each interaction. Its aggregate must be at least 58 fps (vision §6), and its own windows must meet the drop rule. If filtering leaves an even count, the median is the mean of the two central unrounded FPS values; both central runs' windows must meet the existing drop rule. `medianRuns` identifies those two runs, with no fabricated selected run. Display rounding never changes the verdict. Ties use original run order; unmeasured runs sort below measured runs and are not silently discarded. All runs, aggregates, window verdicts, timestamps and before/after host snapshots are retained in `perf.json`.

Why three: eligible probes can still contain an isolated outlier. Median-of-three limits its influence; it does not make a loaded host eligible. This is selection by aggregate, not majority voting on window verdicts: a window failure in a selected central run always fails the interaction. All other runs remain visible evidence.

A window with fewer than four frames cannot support a stable cadence verdict and reports INACTIVE, never PASS. Aggregates exclude those windows, retain their individual verdicts, and are INACTIVE if none qualify. Wrong-route navigation, missing sheet handles, failed probe setup, unsuccessful drags and thrown errors are functional failures: results with `fps: null`, empty windows and an error message stay FAIL on every host, force interaction FAIL and exit 1 even as the only conclusive repetition. Host contention cannot turn them into cadence uncertainty. This is a local frame-cadence benchmark, not a physical-device GPU/presentation measurement: the driver's own input rate bounds the drag window, and host load and display refresh affect results. A conclusive failed repetition or a failed median is a failed gate; do not repeat until it passes.

Preserve each probe's `perf.json` before repeating and distinguish host ineligibility, a baseline failure and a branch regression. A Chrome CDP trace can separate mount/unmount work from the moving interval. The #77 investigation found detached GSAP style restoration temporarily reattaching outgoing controls; restoring their inline styles without measuring removed those extra layouts. Both route panes retain transform/opacity compositing hints during movement; the route stage updates React state on navigation and completion, not on each frame. A profile or a baseline comparison does not override a conclusive failed 58 fps gate.

## Perceiver and completion loop

The wrapper deletes any previous `perceiver.md` first, so a stale answer can never be read as this run's verdict. It then checks `codex exec --help` at runtime and invokes `codex exec --model gpt-6-astra -c model_reasoning_effort=medium --sandbox read-only`. If supported, it attaches every selected PNG with `--image`; otherwise it supplies paths for read-only image tools. The prompt includes absolute screenshot paths and the full product vision and device-class documents. It requests only `CLEAN`, `BLOCKED: <reason>`, or a defect table with `screen | class | severity | what | fix`. Severity is P0/P1/P2/P3, and each defect cites a screenshot. A missing or incomplete capture stops the wrapper before review.

When a review requests the lower contents of a nested scroll pane, capture additional views in the
same run and list their filenames in `<screen>-supplements.json` (a JSON array). Filenames must be
local PNG basenames beginning with that screen ID. The wrapper checks existence and attaches them
to that screen's review, including a full-run review. These are supplemental visual evidence, not
additional machine cases: the original manifest and gate counts remain unchanged. Record the
scroll positions in the filenames and retain the initial BLOCKED answer before reviewing again.

Exit codes are distinct so a reviewer outage is never read as a defect table: 0 CLEAN, 1 defect table, 2 BLOCKED, 3 invocation or format failure (no `codex`, a non-zero `codex` exit such as an exhausted usage limit, an empty answer, or an unparseable answer). Every code 3 prints `perceiver: <reason>` on stderr. A failure before Codex starts (no manifest, empty capture, missing PNGs) leaves no answer file and no process log; its evidence is that stderr line. A failed or malformed Codex answer keeps the raw process output in `perceiver-process.log` and leaves the malformed answer on disk for diagnosis; only a CLEAN, BLOCKED or defect-table answer counts as a verdict. The process is capped at ten minutes. QA itself exits 1 for any failed gate and 2 for inconclusive cadence when no gate failed.

Without a screen argument the wrapper reviews each captured screen in its own invocation, one after another, because one call carrying every PNG of a registry matrix exceeds the model's context (#97). Each screen writes `perceiver-<screen>.md`, `perceiver-<screen>-prompt.md` and `perceiver-<screen>-process.log`; the aggregate `perceiver.md` is `CLEAN` only when every screen is CLEAN, otherwise it concatenates the defect tables under a heading per screen, prefixed with `BLOCKED:` when any screen was blocked. The exit code is the worst screen's. An invocation or format failure on any screen is an outage for the whole run: every screen is still attempted, no aggregate `perceiver.md` is written, the wrapper exits 3 naming each failed screen, and the reasons are in `perceiver-<screen>-process.log` (attach that excerpt in place of the generic log). The stale-verdict cleanup runs before any read or CLI probe. A single-screen invocation still writes `perceiver.md`, `perceiver-prompt.md` and `perceiver-process.log`. Supplemental views declared in `<screen>-supplements.json` are attached to that screen's review in both invocation shapes.

Capture, read the machine report, perceive, fix the identified defects, and re-capture into a new run. Repeat until machine gates pass and a full-run review returns CLEAN. The builder remains responsible for verifying fixes; the perceiver has no write authority. A one-screen review is a scoped diagnostic, never a full-run approval. Module PRs attach the summary and CLEAN result under RULES.md.
